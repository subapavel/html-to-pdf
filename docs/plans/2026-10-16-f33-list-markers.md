# F33 — Outside `disc` / `circle` / `square` list markers are not painted

Date: 2026-10-16. Finding: F33 in `2026-10-15-m0-findings.md`. Status: **done** (§8). The fix goes on `subapavel/blitz`
`htmltopdf/blitz-dom-0.2.4` (base `cd6a5e8`, fix `c1a395e`), carried via `[patch.crates-io]`; fulgur `htmltopdf/srgb-colours` only gets
a smoke test.

## 1. Problem

`<ul><li>` with the default `list-style: disc outside` (and `circle`, `square`) paints no marker; `list-style-position:
inside` paints it, and `<ol>` numbers paint. Tailwind's preflight sets `ol, ul, menu { list-style: none }`, so every
template that wants bullets adds `list-disc` (+ `pl-*`) — and gets none. Probes (`out/scratch/f33/`, Chromium 141 as
reference, A4, 15 mm margin): `ul` default, `circle`, `square`, `disc` with a flex-less `li`, wrapped `li`, `li > p`,
nested `ul` (disc → circle → square): no marker in ours, a marker in Chrome on every one. `ol` outside matches.

## 2. Root cause

Blitz builds the outside marker's Parley layout with a dedicated font stack, not the item's:
`packages/blitz-dom/src/layout/list.rs` `node_list_item_child` (Outside branch) calls `font_for_bullet_style`, which
returns `"Bullet, monospace, sans-serif"` for disc / circle / square / disclosure markers; `ol` markers (`decimal`,
`alpha`) keep the item's own stack (Inter here), which is why they work.

- `Bullet` is Mozilla's bullet face (`assets/moz-bullet-font.otf`), registered only in `BaseDocument::new` when the
  caller passes no `font_ctx` (`document.rs:215-218`). fulgur always passes its own `FontContext`
  (`blitz_adapter.rs:328-334`, bundled faces only), so `Bullet` does not exist.
- `monospace` / `sans-serif` resolve to nothing with `system_fonts(false)` (fontique's generic map is empty; F3b only
  rewrites the keywords in the *document's* CSS, and this stack never goes through CSS).
- Parley drops a run whose stack matches no face (known gap, F3). The marker layout has no glyphs, `extract_marker_lines`
  (`convert/list_marker.rs:156`) returns a line with no items and width 0, and `draw_list_item_marker` draws nothing.

Confirmed: registering Blitz's `moz-bullet-font.otf` via `--font` makes the bullet appear (`out/scratch/f33/bul.pdf`,
flush against the text: that face carries its own side bearing, and the marker layout is the bare character).
`inside` markers are pushed as text into the item's own inline layout (`construct.rs:806-815`, stack = the item's), so
they were never affected. Inter and JetBrains Mono (built-in) both cover U+2022, U+25E6, U+25AA.

## 3. Spec

CSS Lists 3 §3 (the marker box is generated by `::marker`; `list-style-position: outside` puts it outside the principal
block box, in the first line box, so it shares that line's baseline and line height); CSS 2.1 §12.5.1 (outside marker
box placement, "the marker box is outside the principal box"; glyph and exact placement are UA-defined); CSS Counter
Styles 3 §6.1 (`disc`, `circle`, `square` are "similar to" U+2022, U+25E6, U+25AA — a UA may draw them as shapes or use
glyphs); inheritance: `::marker` inherits `font-family` from the list item (CSS Lists 3 §3.1). The item's own stack is
therefore the right default; the special `Bullet` stack is a Blitz convenience.

Chrome draws a 5 px shape at 16 px (`ListMarkerPainter`, `ascent * 2/3` based, 7 px padding). We use the font's glyph,
as Chrome's text-marker path and our own `inside` path do. Measured on `ul` at 16 px Inter (96 dpi): Chrome's bullet is a
5 × 5 px blob at x 80–84, y 84–88 (text starts at x 96.7, baseline 89); ours 5 × 5 px at x 85–89, y 83–87, ink counts
21 / 14 / 24 px against Chrome's 21 / 16 / 25 for disc / circle / square. So the shape and size match, ours sits 5 px
closer to the text and 1 px higher; Chrome's offset is a fixed `ascent * 2/3 + 7 + 1` px, which no glyph advance gives.

## 4. Fix (Blitz, `layout/list.rs`)

In the Outside branch, when the `Bullet` family is not registered in `doc.font_ctx` (`collection.family_id("Bullet")`):

1. keep the item's own font stack (do not override it), so the marker resolves to the item's face and its metrics, line
   height and baseline equal the first line's;
2. lay out `"{char} "` (character + space) as the `inside` path does (`construct.rs:814`), and store the marker as
   `Marker::String("{char} ")` so fulgur's `ShapedGlyph.text_range`s and `marker_to_string` agree (ToUnicode, as for
   `"1. "`). The trailing space is the gap between the bullet and the text, which `Bullet`'s own advance provided.

When `Bullet` is registered (Blitz standalone, fulgur with no bundled fonts and system fonts on) nothing changes, so
fulgur goldens rendered that way stay byte-identical.

Not done: drawing the shapes as vectors like Chrome (a new `ListItemMarker` kind in fulgur's drawables and render path;
independent of fonts, exact Chrome size). Recorded as a possible refinement if a template bundles a font without
U+2022 / U+25E6 / U+25AA (then the marker is dropped silently, as every missing glyph is today).

## 5. Acceptance

case with bundled Inter): disc is a filled dark blob left of the text, vertically inside the cap-height band; circle is
a ring (centre light); square a filled, roughly square blob; nested lists show disc / circle / square; `li > p`; a
wrapped item has one marker, aligned with its first line; `list-style: none` paints nothing; `inside` and `ol` numbers
unchanged (marker still inside the text run, numbers in `pdftotext`); a `<ul>` item taller than a page (F30 split)

them). 06 uses `list-style: disc inside` only because of this finding: switch it to the default outside disc

tests for the marker construction; fulgur `render_smoke` for an outside bullet end to end; example / VRT goldens that
had invisible bullets are re-blessed and named.

## 7. Risks and non-goals

- Goldens in fulgur that render a `ul` with bundled fonts and no `Bullet` face change from invisible bullets to
  visible ones; they are named in the fork commit.
- `<ul style="list-style-type: decimal">` numbers from 2 (`construct.rs:203`: the non-`ol` branch starts the counter at
  1 instead of 0): separate Blitz bug, **F41**, not touched here (outside lists with `decimal` on a `ul` are not a
  template idiom; `ol` is right).
- A bundled face without the glyph paints no marker (Noto Sans has U+2022 but neither U+25E6 nor U+25AA; Inter and
  JetBrains Mono have all three). Without the fulgur guard of §8 Parley shaped GID 0 and a `.notdef` box with no
  Unicode mapping was painted (found by `pdf-reviewer`). Drawing the shapes as vectors (§4, "Not done") removes the
  dependency.
- `disclosure-open` / `disclosure-closed` share `font_for_bullet_style` and get the same fix; `▾` / `▸` coverage depends
  on the bundled face (not in Inter's default subset check here).
- RTL: `<ul dir=rtl>` is not mirrored by our engine at all (the text stays at the left edge; Chrome puts it at the right
  and the bullet right of it), so there is nothing marker-specific to fix; outside markers are drawn left of the item
  (`render.rs:3599`). Out of scope.
- `li { display: flex }` has no marker in Chrome either (not a list item); ours matches.

## 8. Result

- Blitz fork `c1a395e` (`list.rs`: `outside_marker`, 3 unit tests); fulgur fork `1b98931` + `6aacc0f` (`render_smoke` test,
  red without the Blitz fix only with `system_fonts(false)`: with host fonts `monospace` resolves to a host face and the
  old stack painted a bullet from it). No golden changed: the examples, the VRT fixtures and the tagged-pdf example render
  with system fonts, where Blitz registers its own `Bullet` face, and are byte-identical. Probes of §1 now match Chrome:
  disc / circle / square, nested disc → circle → square, wrapped item, `li > p`, `li > div`, `ol`; a `display: flex`
  item has no marker in either.
- fulgur fork `314df1d` (`list_marker.rs`: `drop_notdef_marker`): an outside marker whose glyph run contains GID 0 is
  not painted and a warning is logged, instead of a `.notdef` box with no ToUnicode entry (PDF/A-2 §6.2.11.8,
  PDF/UA-1 §7.21.7–8). Found by `pdf-reviewer` with Noto Sans and `circle` / `square`; 2 unit tests and a
  `render_smoke` test counting CID 0 in text strings (red before). Inside markers and running text that use a glyph
  the face lacks are F44.
- `crates/htmltopdf/tests/list_markers.rs` 10 tests (7 red before the fix); fixtures 01–05 and 07 byte-identical; 06 now
  uses the default outside disc (`class="pl-4" style="list-style: disc"`, `list-disc` is not in the committed
  `tailwind.css`), Chrome reference regenerated: page 1 15.9 % (unchanged), page 2 12.5 → 11.8 %, threshold unchanged
  (it follows the worst page).
